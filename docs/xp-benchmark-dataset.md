# Fixed 10M-star XP benchmark

The CPU-only builder `scripts/benchmarks/build_xp_benchmark.py` samples 9M training and 1M validation stars without replacement, proportionally across the original HDF5 shards. Validation membership follows the epoch-27 checkpoint. Seed 42 fixes selection. Every original record field is retained, including G-normalized XP coefficients, their errors and unmodified magnitudes. Scaling is applied in the training reader; the parent checkpoint path identifies the existing RobustScaler for matched continuations.

Each split has `records` (original compound dtype), `source_shard`, `source_row`, packed `xp_correlations` (stars × BP/RP × 1485), `xp_band_metadata` and `xp_covariance_available`. Band metadata retain basis IDs, parameter counts, relevant-basis counts and standard deviations. Correlations have implicit unit diagonal, with strict lower-triangle ordering. The loader reconstructs covariance from coefficient errors, and divides by both scaler scales. G-normalization uncertainty and BP/RP cross covariance are not supplied by this sidecar. No spectra are MC sampled.

Source IDs are indexed once in memory for the selected 10M stars. Original CSV shards are streamed concurrently, returning only selected rows to the single HDF5 writer. The complete source table is scanned once for sampling. Duplicate IDs, invalid correlations or missing covariance matches fail the build. An existing output is never overwritten. The `.building` file and manifest are partial products; only a successful round-trip/coverage check publishes the final `.h5`.

The grouped layout requires a reader selecting `train/records` or `validation/records`; it is not a drop-in replacement for the existing root-shard loader. Values in records remain in stored-table units, before RobustScaling. Interpret unavailable measurements using the existing field-cleaning conventions. New scalers must be fit only on the training split.

Packed float32 correlations alone require 118.8 GB (110.6 GiB), plus records and metadata before compression. Runtime depends on scanning/decompressing the entire raw CSV collection, not merely parsing the selected 10M stars. The one-CSV timing is therefore not an end-to-end production estimate. Final outputs belong on ARC; random writes belong on scratch.

Behavioral verification: `pixi run pytest tests/test_xp_benchmark.py -q`.

Random correlation writes use uncompressed contiguous HDF5 staging under `--scratch-dir` on `/scratch`. This needs roughly 140 GB of local disk, but does not require that much RAM: the kernel page cache is bounded by the session memory limit. Once staging passes coverage checks, publication reads sequential blocks and writes a compressed `.copying` file on ARC. Schema and beginning/middle/end values are compared before atomic rename to the final file. Scratch staging is removed only after successful publication.

The reader uses spawned processes, each initialized once with the sorted sample IDs. It filters physical CSV lines by source ID before tokenizing the quoted array columns. On CANFAR session `kshsrl62`, four reads of the same 1.43 GB compressed shard took 111.55 seconds with the previous Pandas thread pool and 27.15 seconds with filtering plus four processes. All methods returned the same 3,749 IDs and packed correlations, checked by SHA-256. This measures the reader workload, not total build time. Replacing threads with processes is essential: the filtered reader with four threads took 144.53 seconds.

`--hdf5-base-url` instead fetches each corresponding Flatiron `.hdf5` shard temporarily into worker scratch, selects typed arrays by source ID, then removes the downloaded shard. The CSV filenames provide the shard inventory; their contents are not parsed in this mode. Session `kztiua72` measured 10.37 seconds to download a 1.16 GB shard and 0.21–0.25 seconds to read its selected correlations, versus 26.72 seconds for a warm CSV read. Selected IDs and float32 correlations were byte-identical. Binary metadata retain the archive's stored precision. This does not establish collection-wide bandwidth or completion time.

`--reuse-sample PATH` copies records, row/shard provenance and the reference scaler from a retained grouped HDF5 sample into new scratch staging. Counts, schema, original split shard names and parent checkpoint path must match. Supply `--expected-source-id-sha256` to enforce the original sample identity. Existing files are read only and never overwritten; correlations are rebuilt from the selected raw source. A stopped session's private scratch cannot be recovered by another session.
